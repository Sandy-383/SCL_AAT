PART 1 — THE PROBLEM  (point to SYSTEM_ARCHITECTURE.png — Stage 1)
────────────────────────────────────────────────────────────────────────────────

"Imagine you are in charge of designing bus routes for Bangalore.
You have 50 bus stops spread across the city.
You need to create 10 bus routes that serve as many people as possible.

But here is the challenge — you have FOUR conflicting goals at the same time:

  Goal 1 — Make passengers reach fast         → minimize travel time
  Goal 2 — Avoid too many bus changes          → minimize transfers
  Goal 3 — Keep the bus company's cost low     → minimize fleet cost
  Goal 4 — Serve as many people as possible    → maximize demand coverage

The conflict is: if you add more routes to cover everyone,
the cost goes up. If you reduce cost, coverage drops.
There is no single perfect answer.

This is called a Multi-Objective Optimization Problem.
And it is NP-Hard — meaning brute force search is impossible
even for a computer. That is why we need AI."

PART 3 — K-MEANS CLUSTERING  (point to SYSTEM_ARCHITECTURE.png — Stage 2)
────────────────────────────────────────────────────────────────────────────────

"Before we run the optimizer, we do something smart.

Previously, in older systems, routes were generated randomly —
just pick random stops and connect them. That is inefficient.

We improved this using K-Means Clustering.

K-Means is a machine learning algorithm that groups similar items together.
We apply it to the geographic coordinates — latitude and longitude — of all
50 bus stops.

It groups the 50 stops into 10 geographic clusters.
Each cluster becomes the starting point for one bus route.

So instead of random routes, our optimizer starts with routes that are
already geographically meaningful — stops that are physically close
together are grouped into the same route.

Think of it like this:
  Old way → randomly assign stops to routes → wasteful, slow to improve
  New way → K-Means groups nearby stops → routes make geographic sense
             from the very beginning

This is the first stage of our two-stage pipeline:
  Stage 1: K-Means gives us smart initial routes
  Stage 2: Grey Wolf Optimizer improves them further"

PART 4 — THE GREY WOLF OPTIMIZER  (point to SYSTEM_ARCHITECTURE.png — Stage 3)
────────────────────────────────────────────────────────────────────────────────

"Now comes the main algorithm — the Grey Wolf Optimizer, or GWO.

GWO is inspired by how grey wolves hunt in nature.
In a wolf pack, there is a strict hierarchy:

  Alpha  — the best wolf    — the pack leader
  Beta   — second best      — second in command
  Delta  — third best       — third in command
  Omega  — all others       — the followers

In our system, each wolf is not a real wolf —
it is a CANDIDATE ROUTE PLAN for the bus network.

We have 50 wolves, meaning 50 different possible bus route plans.
Each route plan is represented as a set of numbers — a vector of 220 values.
These 220 numbers encode which stops each route visits, how often buses run,
and how many vehicles are assigned.

Every iteration, each wolf looks at the Alpha, Beta, and Delta wolves —
the three best route plans found so far —
and adjusts its own plan to be more like them.

Over 50 iterations, all 50 wolves converge toward better and better
route plans. At the end, we have a set of optimal solutions called
the Pareto Front — where each solution is a different trade-off
between our four goals."


────────────────────────────────────────────────────────────────────────────────
PART 5 — THE GPU  (point to GPU sub-panel in architecture)
────────────────────────────────────────────────────────────────────────────────

"Now the most important part — why do we need a GPU?

In each iteration, we have 50 wolves, and each wolf has 220 numbers to update.
That is 50 times 220 = 11,000 calculations per iteration.

On a normal CPU, these 11,000 calculations happen one by one — sequentially.

On our NVIDIA RTX 4060 GPU, all 11,000 calculations happen
AT THE SAME TIME — in parallel.

We wrote a CUDA kernel — a special GPU program — that assigns one thread
to each wolf-dimension combination. So 11,000 threads run simultaneously
on the GPU's 3072 CUDA cores.

The best part — you don't need to install any CUDA toolkit.
Our code compiles the GPU program automatically at runtime using
a technology called NVRTC — NVIDIA Runtime Compilation.
Just install Python and run the program.

The result:
  CPU handles fitness evaluation — complex graph logic
  GPU handles position updates — pure parallel math
  Together they form a hybrid system that is fast and accurate."

COMMON QUESTIONS AND ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: Why Grey Wolf Optimizer and not Genetic Algorithm?
A: GWO has only one parameter — 'a' which decreases automatically from 2 to 0.
   GA needs crossover rate, mutation rate, and selection pressure to be tuned.
   GWO's simplicity makes it easier to parallelize on GPU.
   Also our results show CUDA-GWO achieves better demand coverage than GA.

Q: Why not just use Google Maps data?
A: Google Maps data is proprietary. Our system supports real GTFS data —
   the open standard used by transit agencies worldwide.
   If GTFS files are placed in the data/gtfs folder, the system
   automatically uses real data instead of the synthetic city.

Q: What is the Pareto Front?
A: When you have multiple objectives that conflict, there is no single
   best solution. Instead there is a set of solutions where improving
   one objective necessarily worsens another. That set is the Pareto Front.
   For example — Route plan A has lower travel time but higher cost.
   Route plan B has lower cost but higher travel time.
   Neither is strictly better — both are on the Pareto Front.
   The decision-maker picks based on their priority.

Q: How much faster is GPU than CPU?
A: For the position update step alone, the GPU handles 11,000 operations
   in parallel instead of sequentially. At 50 stops, overall speedup is
   modest because CPU fitness evaluation dominates. The real GPU advantage
   appears at 200-500 stops where the position update becomes the bottleneck.

Q: Why is the fitness evaluation on CPU and not GPU?
A: Fitness evaluation requires finding shortest paths in a graph,
   detecting transfers between routes, and working with variable-length
   route sequences. These involve heavy branching and irregular memory access
   which GPUs handle poorly. We use a hybrid design —
   GPU for the parallel math, CPU for the complex graph logic.

Q: What does f4 = 0.030 mean?
A: f4 is the demand coverage gap. f4 = 0 means 100% of passenger demand
   is covered. f4 = 0.030 means 3% of demand is not served by any route.
   So our CUDA-GWO covers 97% of all passenger demand in the city —
   which is the best balanced result among all five algorithms.

Q: Can this scale to a real city like Bangalore with 500 stops?
A: Yes. Run: python main.py --stops 500
   The algorithm scales — with more stops, the GPU advantage increases
   because the 220-dimensional space grows to 2200 dimensions,
   making the parallel position update more significant.
